# Requirements Document

## Introduction

This feature bundles a set of bug fixes and new capabilities for the ScrubAI image
metadata cleaner workspace (the `CleanerInterface` and its supporting hooks and
config). The workspace is the product's main user-facing surface: users drop images
into the browser, the canvas redraws them pixel-by-pixel, and a re-exported file is
produced with controlled metadata. All work is client-side, and the privacy
invariant (image bytes never leave the browser) is a hard constraint that every
requirement below must preserve.

The bundle covers six areas:

1. Make output-format and camera-profile controls resilient to browser translation extensions.
2. Centralize all tier limits into `src/config/pricing.ts`, including a new `user_free` tier for signed-up free users.
3. Implement real EXIF injection for camera profiles (and a truly sterile "None" option).
4. Provide a real sample image with genuine pixels and realistic metadata.
5. Ensure the export quality slider affects JPEG/WebP output.
6. Anchor the options/controls block to the bottom of the left column with whitespace above it.

## Glossary

- **Workspace**: The `CleanerInterface` React component that hosts the drop zone, image queue, controls, and audit panel.
- **Canvas_Engine**: The `useCanvasEngine` hook that converts, resizes, re-encodes, and container-scrubs image bytes client-side.
- **EXIF_Injector**: The client-side component that writes valid EXIF tags into an encoded JPEG/WebP byte stream after the container scrub.
- **Pricing_Config**: The central configuration module `src/config/pricing.ts` that is the single source of truth for prices and tier limits.
- **Auth_Provider**: The `useAppAuth()` hook returning `{ isSignedIn, isPro, userId, isLoaded }`.
- **Tier**: A usage class. One of: `guest_free` (anonymous, not signed in), `user_free` (signed in via Clerk, free plan), or `pro` (paid, unlimited).
- **Daily_Clean_Limit**: The maximum number of cleans a non-pro Tier may perform in a calendar day.
- **Camera_Profile**: A selectable metadata identity. One of: `iphone`, `canon`, `sony`, or `none`.
- **Output_Format**: The selected export container. One of: `auto`, `image/png`, `image/jpeg`, `image/webp`.
- **Export_Quality**: A numeric value from 0.1 to 1.0 controlling lossy encode quality for JPEG/WebP.
- **Sample_Image**: A built-in demonstration image generated by the "Try a sample" action.
- **Options_Block**: The grouped controls section containing filename, camera profile, quality slider, output format, and the action row.
- **Translation_Extension**: A browser extension (e.g. Google Translate) that mutates the page DOM by wrapping or replacing text nodes.

## Requirements

### Requirement 1: Translation-resilient output controls

**User Story:** As a user with a browser translation extension active, I want the output-format and camera-profile controls to remain visible and usable, so that I can configure my export regardless of DOM mutations injected by the extension.

#### Acceptance Criteria

1. WHILE a Translation_Extension is mutating text nodes in the Workspace, THE Workspace SHALL keep the Output_Format control, the Output_Format label, and the Camera_Profile control present in the DOM and rendered with non-zero layout dimensions (not set to display:none, visibility:hidden, or zero width/height).
2. WHILE a Translation_Extension is active, THE Workspace SHALL keep the camera-profile and output-options section interactive such that each control can receive focus and accept a value change through pointer and keyboard input.
3. THE Workspace SHALL mark the Output_Format label, the Camera_Profile label, and their option text with translation-resilience attributes so that a Translation_Extension does not remove or hide the associated controls.
4. WHEN a Translation_Extension wraps the label text of the Output_Format or Camera_Profile control in one or more additional DOM nodes, THE Workspace SHALL continue to associate each label with its correct control such that activating the label moves focus to that control.
5. IF a Translation_Extension alters the visible option text of the Output_Format or Camera_Profile control, THEN THE Workspace SHALL retain the original underlying option value, and the value applied to the export SHALL equal the value selected before the text was altered.
6. THE Workspace SHALL apply the translation-resilience marking to the Output_Format and Camera_Profile controls using attribute-based markers that are not tied to any single Translation_Extension product or version, such that the controls remain present and rendered per criterion 1 across any active Translation_Extension.

### Requirement 2: Centralized tier limits in Pricing_Config

**User Story:** As a developer, I want every tier limit defined in one config module, so that limits are consistent across the UI and logic and are easy to change.

#### Acceptance Criteria

1. THE Pricing_Config SHALL define, for each Tier, a Daily_Clean_Limit, a maximum batch size expressed as a positive integer count of images, and a maximum upload size expressed in megabytes as a positive number.
2. THE Pricing_Config SHALL define a Daily_Clean_Limit of 5 for the `guest_free` Tier.
3. THE Pricing_Config SHALL define a Daily_Clean_Limit of 10 for the `user_free` Tier.
4. THE Pricing_Config SHALL define the `pro` Tier as having no Daily_Clean_Limit, representing an unlimited number of cleans per calendar day.
5. THE Workspace SHALL read the Daily_Clean_Limit, the maximum batch size, and the maximum upload-size limit for the current Tier from the Pricing_Config rather than from hardcoded literals.
6. WHILE the current Tier is a non-pro Tier, WHEN the Workspace evaluates whether a clean is permitted, THE Workspace SHALL permit the clean if the persisted daily clean count for the current calendar day is less than the Daily_Clean_Limit for the current Tier.
7. IF the current Tier is a non-pro Tier and the persisted daily clean count for the current calendar day is greater than or equal to the Daily_Clean_Limit for the current Tier, THEN THE Workspace SHALL deny the clean, SHALL leave the persisted daily clean count unchanged, and SHALL indicate that the daily limit has been reached.
8. WHILE the current Tier is `pro`, WHEN the Workspace evaluates whether a clean is permitted, THE Workspace SHALL permit the clean regardless of the persisted daily clean count.
9. WHEN the calendar day changes relative to the calendar day stored with the persisted daily clean count, THE Workspace SHALL treat the persisted daily clean count for the new calendar day as 0.

### Requirement 3: Correct tier resolution for signed-up free users

**User Story:** As a signed-up free user, I want a daily limit of 10 cleans instead of 5, so that creating an account gives me a tangible benefit over anonymous use.

#### Acceptance Criteria

1. WHILE the Auth_Provider reports `isLoaded` is true and `isSignedIn` is false, THE Workspace SHALL resolve the current Tier to `guest_free`.
2. WHILE the Auth_Provider reports `isLoaded` is true, `isSignedIn` is true, and `isPro` is false, THE Workspace SHALL resolve the current Tier to `user_free`.
3. WHILE the Auth_Provider reports `isLoaded` is true and `isPro` is true, THE Workspace SHALL resolve the current Tier to `pro`.
4. WHILE the Auth_Provider reports `isLoaded` is false, THE Workspace SHALL resolve the current Tier to the most restrictive default of `guest_free`.
5. WHILE the current Tier is `user_free`, THE Workspace SHALL set the Daily_Clean_Limit to 10 cleans within a calendar day, where a calendar day starts at 00:00:00 local time and resets at the next 00:00:00 local time.
6. WHILE the current Tier is `guest_free`, THE Workspace SHALL set the Daily_Clean_Limit to 5 cleans within a calendar day, where a calendar day starts at 00:00:00 local time and resets at the next 00:00:00 local time.
7. WHEN the Auth_Provider reports `isSignedIn` changes from false to true within a session, THE Workspace SHALL recompute the current Tier from the current authentication state and apply the corresponding Daily_Clean_Limit before processing the next clean request.
8. IF a clean is requested while the persisted daily clean count for the current Tier has reached its Daily_Clean_Limit, THEN THE Workspace SHALL reject the clean, SHALL present an indication that the daily limit has been reached, and SHALL leave the persisted daily clean count unchanged.

### Requirement 4: Tier-accurate limit text

**User Story:** As a user, I want the on-screen clean-count and limit text to reflect my actual daily limit, so that the displayed limit matches the limit that is enforced.

#### Acceptance Criteria

1. THE Workspace SHALL display the daily clean-count text using the Daily_Clean_Limit value of the current Tier, such that the value shown in the clean-count badge, the used-today text, and the per-day allowance text are identical for that Tier.
2. WHILE the current Tier is `guest_free`, THE Workspace SHALL display the daily limit as the integer 5 in the clean-count badge, the used-today text, and the per-day allowance text.
3. WHILE the current Tier is `user_free`, THE Workspace SHALL display the daily limit as the integer 10 in the clean-count badge, the used-today text, and the per-day allowance text.
4. WHILE the current Tier is `pro`, THE Workspace SHALL display an unlimited-cleans indicator in place of a numeric daily limit in the clean-count badge, the used-today text, and the per-day allowance text, and SHALL treat the numeric daily limit value as the integer 0 for display purposes.
5. WHEN the persisted daily clean count reaches the Daily_Clean_Limit for a Tier other than `pro`, THE Workspace SHALL display the limit-reached message using that same Daily_Clean_Limit value (5 for `guest_free`, 10 for `user_free`).
6. WHILE the current Tier is `pro`, THE Workspace SHALL use a limit-reached message value of the integer 0 and SHALL never display the limit-reached message.
7. WHEN the current Tier changes from one value to another, THE Workspace SHALL update the clean-count badge, the used-today text, and the per-day allowance text to the Daily_Clean_Limit of the new Tier within 1 second.
8. IF the current Tier cannot be determined, THEN THE Workspace SHALL display the daily limit using the `guest_free` Daily_Clean_Limit value of 5 across the clean-count badge, the used-today text, and the per-day allowance text.

### Requirement 5: Real EXIF injection for camera profiles

**User Story:** As a user, I want a selected camera profile to write real EXIF tags into my exported image, so that the output carries the metadata identity shown in the report rather than only a displayed mock.

#### Acceptance Criteria

1. WHEN a Camera_Profile other than `none` is selected and an image is cleaned, THE EXIF_Injector SHALL write the EXIF tags Make, Model, LensModel, Software, and DateTimeOriginal into the exported file, where DateTimeOriginal is encoded in valid EXIF datetime format (`YYYY:MM:DD HH:MM:SS`).
2. WHEN the `iphone`, `canon`, or `sony` Camera_Profile is selected, THE EXIF_Injector SHALL write the Make and Model values defined for the selected profile.
3. WHEN an exported file carries injected EXIF tags, THE injected tags SHALL be parseable by an EXIF parser without error as a structurally valid EXIF block.
4. FOR ALL Camera_Profiles other than `none`, injecting a profile into an image and then reading the exported file SHALL yield Make, Model, LensModel, Software, and DateTimeOriginal values byte-for-byte identical to the values that were injected (round-trip property).
5. WHEN the EXIF_Injector writes injected tags, THE EXIF_Injector SHALL perform injection after the Canvas_Engine container scrub step, such that reading the exported file yields zero source-derived metadata tags (EXIF, GPS, IPTC, XMP, C2PA) alongside the injected tags.
6. WHILE the EXIF_Injector performs injection, THE EXIF_Injector SHALL operate only on in-browser byte buffers and SHALL NOT transmit image bytes over the network.
7. IF the Output_Format is a container that cannot carry the injected EXIF block (for example PNG), THEN THE EXIF_Injector SHALL leave the exported pixel data byte-for-byte intact and SHALL expose an observable indication to the caller that injection was not applied.
8. IF injection fails on a container that supports EXIF (for example JPEG or WebP), THEN THE EXIF_Injector SHALL leave the exported pixel data byte-for-byte intact, SHALL NOT write a partial EXIF block, and SHALL expose an observable error indication to the caller.

### Requirement 6: Sterile output for the None profile

**User Story:** As a privacy-focused user, I want the "None (sterile)" option to produce a file with no metadata at all, so that I can export an image that carries no identifying tags.

#### Acceptance Criteria

1. WHEN the `none` Camera_Profile is selected and an image is cleaned, THE Canvas_Engine SHALL produce an exported file that contains zero EXIF, XMP, IPTC, ICC, and C2PA metadata segments.
2. WHEN an exported file produced with the `none` Camera_Profile is parsed with an EXIF parser, THE Canvas_Engine SHALL produce a file for which the parser returns zero metadata tags across all of the EXIF, XMP, IPTC, ICC, and C2PA categories.
3. WHEN the `none` Camera_Profile is selected, THE EXIF_Injector SHALL NOT write any Camera_Profile EXIF tags into the exported file.
4. IF metadata removal for the `none` Camera_Profile fails such that any EXIF, XMP, IPTC, ICC, or C2PA metadata would remain in the output, THEN THE Canvas_Engine SHALL NOT produce an exported file and SHALL present an error indication that the sterile export could not be completed, leaving the source image unmodified.
5. WHEN the `none` Camera_Profile is selected and an image is cleaned, THE Canvas_Engine SHALL produce an exported file that retains the visible pixel content of the source image at the source image's original width and height in pixels.

### Requirement 7: Real sample image

**User Story:** As a first-time user, I want the "Try a sample" button to load a real, viewable image, so that I can see the audit and cleaning flow operate on genuine pixels.

#### Acceptance Criteria

1. WHEN the user activates the "Try a sample" action, THE Workspace SHALL create a Sample_Image from bundled bitmap pixel data without performing any network fetch.
2. THE Sample_Image SHALL be decodable by the browser as a viewable image with a width of at least 1 pixel and a height of at least 1 pixel.
3. THE Sample_Image SHALL have an encoded byte size no greater than 51200 bytes (50 KB).
4. THE Sample_Image SHALL carry embedded source metadata containing at least one tag from each of the EXIF, GPS, and Content Credentials categories so that the audit step reports at least one risk-bearing tag.
5. WHEN the Sample_Image is cleaned, THE Canvas_Engine SHALL process the Sample_Image through the same pixel-redraw and export pipeline used for user-supplied images, producing an output image whose metadata contains zero EXIF, GPS, IPTC, XMP, and Content Credentials tags.
6. WHEN the user activates the "Try a sample" action, THE Workspace SHALL evaluate the current Tier Daily_Clean_Limit before adding the Sample_Image.
7. IF the current Tier Daily_Clean_Limit has been reached when the user activates the "Try a sample" action, THEN THE Workspace SHALL reject the action, SHALL NOT add the Sample_Image, and SHALL present an indication that the daily clean limit has been reached.

### Requirement 8: Effective export quality control

**User Story:** As a user, I want the export quality slider to actually change my output, so that I can trade file size against image fidelity for lossy formats.

#### Acceptance Criteria

1. WHEN an image is exported and the Output_Format is JPEG or WebP, THE Canvas_Engine SHALL pass the current Export_Quality value to the canvas encode step.
2. WHEN two exports of the same source image use a higher Export_Quality value and a lower Export_Quality value for the same JPEG or WebP Output_Format, THE Canvas_Engine SHALL produce an output file at the lower Export_Quality value whose byte size is less than or equal to the output file at the higher Export_Quality value, and SHALL produce differing byte sizes for any two Export_Quality values that differ by at least 0.1.
3. WHEN the Output_Format is PNG, THE Workspace SHALL disable the Export_Quality control and display a visible indication that quality does not apply to PNG output.
4. WHEN the Export_Quality slider value changes, THE Workspace SHALL store the updated value and use that stored value for the next export without requiring any additional user action.
5. IF the Export_Quality value is below 0.1, THEN THE Canvas_Engine SHALL clamp it to 0.1 before encoding.
6. IF the Export_Quality value is above 1.0, THEN THE Canvas_Engine SHALL clamp it to 1.0 before encoding.

### Requirement 9: Options block anchored to the bottom of the left column

**User Story:** As a user, I want the controls grouped at the bottom of the workspace with space above them, so that the image thumbnails have breathing room and the layout does not feel crowded.

#### Acceptance Criteria

1. WHILE one or more images are present in the queue, THE Workspace SHALL render the Options_Block flush against the bottom edge of the left column container, with no other left column content positioned below it.
2. WHILE one or more images are present in the queue, THE Workspace SHALL render a vertical gap of at least 16 pixels between the lowest image queue thumbnail and the top edge of the Options_Block.
3. THE Options_Block SHALL contain the filename control, the Camera_Profile control, the Export_Quality control, the Output_Format control, and the action row, rendered in that top-to-bottom order.
4. WHILE the combined height of the image queue and the Options_Block is less than the available vertical height of the left column container, THE Workspace SHALL anchor the Options_Block to the bottom edge of the left column container such that the vertical gap above the Options_Block expands to fill the remaining space.
5. WHILE the combined height of the image queue and the Options_Block exceeds the available vertical height of the left column container, THE Workspace SHALL keep the Options_Block fully visible at the bottom edge of the left column container and confine overflow to the image queue region.
6. IF zero images are present in the queue, THEN THE Workspace SHALL NOT render the Options_Block.
